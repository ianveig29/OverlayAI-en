======================================================================
1. OBJETIVO Y ALCANCE REAL
======================================================================

El Inventory Changer de OverlayAI es un sistema local. OverlayAI mantiene una
coleccion propia, un loadout propio y aplica determinados cambios visuales o de
estado exclusivamente en el cliente de CS2.

El sistema NO:

- Crea objetos reales en Steam.
- Modifica el inventario del backend.
- Envia mensajes falsos al Game Coordinator.
- Otorga ownership real de un objeto.
- Hace que otros jugadores vean el inventario local.
- Inserta actualmente objetos falsos en SOCache.

La arquitectura actual separa cuatro responsabilidades:

1. OverlayAI.exe: catalogo, coleccion, Configs, menu y fuente de verdad.
2. Servidor IPC local: comunica estados y acciones mediante JSON versionado.
3. InventoryBridge.dll: codigo interno minimo para operaciones que un external
   no puede realizar correctamente, como modelos y animaciones.
4. Frontends de prueba: InventoryHost y el prototipo Panorama desacoplado.

- Controller: m_iMusicKitID.

Protecciones implementadas:

- Captura del estado original antes de escribir.
- WriteIfDifferent para evitar escrituras repetidas.
- Restauracion al desactivar, desequipar, eliminar, cerrar Overlay o perder el
  contexto valido.
- No se intenta restaurar sobre direcciones pertenecientes a otra entidad.

Se probaron:

- Agregar kits existentes a la coleccion local.
- Equiparlos.

- Restaurar el kit original.
- Mantener el estado al controlar un bot sin escribir sobre un contexto viejo.

Limitacion:

7. SERVIDOR IPC LOCAL
======================================================================

Archivos principales:

- OverlayAI\src\InventoryIpcServer.cpp/.h
- OverlayAI\src\InventoryIpcController.cpp/.h
- OverlayAI\src\InventoryProtocol.cpp/.h
- OverlayAI\src\InventoryLog.cpp/.h

Nombre del named pipe:
\\.\pipe\OverlayAI.Inventory.v1

Caracteristicas del transporte:

- Pipe duplex local.
- Rechazo de clientes remotos.
- Acceso permitido al mismo usuario de Windows, administradores y SYSTEM.
- Etiqueta de integridad media para permitir que CS2 normal se conecte a un
  Overlay elevado.
- Frames con prefijo uint32 de longitud.
- Tamano maximo por frame: 256 KiB.
- Maximo de 128 frames en las colas internas.
- Timeout de respuesta de 5 segundos.
- Worker dedicado; no bloquea el render de ImGui.
- Contadores de recibidos, enviados y rechazados.
- Liberacion de pipe, thread, colas y handles durante Stop.

El hilo del servidor recibe bytes y los coloca en una cola. El hilo principal
de OverlayAI llama InventoryIpcController::Pump y procesa hasta 32 comandos por
frame. De esta forma las acciones que modifican el estado del programa ocurren
en el contexto controlado del Overlay y no dentro del worker de transporte.

Seguridad logica del protocolo:

- protocol_version obligatorio.
- message_type obligatorio.
- request_id obligatorio.
- payload validado por tipo y rango.
- Limite de sesiones recordadas: 8.
- Limite de request IDs recordados por sesion: 256.
- Rechazo de duplicados para evitar repetir acciones no idempotentes.
- Errores estructurados mediante protocol.error.

Mensajes de entrada soportados:

- client.hello
- inventory.request_refresh
- inventory.equip
- inventory.unequip
- inventory.remove
- inventory.duplicate
- inventory.inspect
- inventory.close_reveal

Mensajes de salida principales:

- inventory.snapshot
- inventory.item_added
- inventory.item_removed
- inventory.loadout_changed
- inventory.reveal_closed
- inventory.apply_failed
- protocol.error

El snapshot incluye la coleccion, loadout, seleccion, pending reveal, metadatos
de catalogo y offsets runtime necesarios para el bridge. No se envian punteros
entre procesos.

8. INVENTORY HOST: CLIENTE DE PRUEBA
======================================================================

OverlayAI.InventoryHost.exe es un cliente CLI separado. Se creo para validar
el servidor y el contrato antes de depender de Panorama.

Comandos disponibles:

- list [--json]
- watch [iteraciones] [intervalo_ms] [--json]
- equip <local_id> [t|ct|both]
- unequip [local_id] [t|ct|both]
- duplicate <local_id>
- remove <local_id>
- inspect <local_id>
- close-reveal <local_id>

El host:

1. Se conecta al named pipe.
2. Envia client.hello con una sesion propia.
3. Recibe un inventory.snapshot.
4. Envia una accion versionada.
5. Imprime la respuesta y, cuando corresponde, solicita otro snapshot.

Esta herramienta permitio probar preload, save/load, equipamiento y cambios de
loadout sin inyectar primero una interfaz Panorama.

10. INVENTORY BRIDGE INYECTADO
======================================================================

Archivo principal:
OverlayAI.InventoryBridge\InventoryBridge.cpp

La DLL existe porque un external no puede cambiar correctamente ciertos
modelos, reconstruir subclass, utilizar animaciones ni interceptar eventos del
cliente en el momento apropiado.

Objetos nombrados usados por el bridge:

- Local\OverlayAI.InventoryBridge.Stop
- Local\OverlayAI.InventoryBridge.Ready
- Local\OverlayAI.InventoryBridge.Singleton

Inicio:

1. DllMain crea un worker y desactiva notificaciones de threads.
2. El worker evita dos instancias mediante el mutex Singleton.
3. Resuelve interfaces Source2Client002, Source2EngineToClient001 y
   PanoramaUIEngine001.
4. Escanea firmas verificadas de la build actual.
5. Instala los hooks necesarios.
6. Se conecta periodicamente al pipe de OverlayAI.
7. Publica un snapshot interno solamente cuando cambia su hash.

Firmas/funciones verificadas en la build documentada:

- SetModel.
- UpdateSubclass.
- FindHudElement.
- ClearHudWeaponIcon.
- InventoryManager como diagnostico de investigacion.

El bridge valida memoria con VirtualQuery antes de leer o escribir y envuelve
las llamadas internas de mayor riesgo con SEH cuando corresponde.

13. HUD Y KILLFEED DEL CUCHILLO
======================================================================

HUD:

- Se limpia el cache de descripcion del C_EconItemView.
- Se obtiene HudWeaponSelection.
- Se llama la funcion interna validada para limpiar/reconstruir iconos.
- El refresco ocurre con retraso y un numero limitado de intentos.

Esto permite que el selector de armas muestre el Butterfly. La tienda usa otro
panel/loadout y puede mostrar brevemente el cuchillo default; queda separado
como una mejora Panorama/HUD posterior.

Killfeed:

- Se resuelve el game event manager.
- Se registra un listener de player_death.
- Se instala un pre-hook de FireEventClientSide para cambiar el evento antes de
  que Panorama lo consuma.
- El listener registrado queda como fallback y no procesa dos veces cuando el
  pre-hook esta activo.
- Solo se modifica el evento si el atacante es el local player.
- weapon cambia de knife/knife_t a knife_butterfly.

Bug de soltar y recoger:

Despues de recoger el cuchillo, Panorama priorizaba los campos economicos del
evento y mostraba el icono default aunque weapon ya fuera knife_butterfly.

La solucion fue modificar solo el evento local player_death:

- weapon_itemid = 0
- weapon_fauxitemid = 18446744069414584835

Ese faux ID equivale a 0xFFFFFFFF00000203 y describe definition index 515.
No crea un item ni modifica ownership; solo proporciona identidad visual al
evento de killfeed.

Se comprobo killfeed correcto como jugador y al controlar bots.

14. CICLO DE VIDA, RESTAURACION Y CRASHES CORREGIDOS
======================================================================

Problemas encontrados durante las pruebas:

- Restaurar/reaplicar en cada cambio de arma llamaba UpdateSubclass demasiadas
  veces.
- Reinicios de ronda podian dejar punteros de entidades expiradas.
- mp_restartgame podia invalidar el arma antes de restaurarla.
- Un mapa con Butterfly nativo no debia recibir otra mutacion.
- Soltar/recoger cambia la identidad y el handle de la entidad.

Protecciones actuales:

- El Butterfly permanece aplicado al cambiar temporalmente a pistola/rifle.
- No se restaura y reaplica en cada weapon switch.
- Se guarda el handle completo, no solo el indice bajo.
- Antes de restaurar se resuelve nuevamente el handle y se compara con el
  handle real de la entidad.
- Se compara last spawn time para detectar un nuevo spawn.
- Una entidad expirada se descarta sin escribir sobre memoria reutilizada.
- Un Butterfly nativo con definition/subclass correctos no llama UpdateSubclass.
- Shutdown espera la restauracion dentro de un plazo limitado y luego retira
  hooks limpiamente.

Se analizaron crashes con WER/dumps. Uno de ellos ocurria dentro de
UpdateSubclass tras una transicion insegura. Las validaciones anteriores y la
reduccion de llamadas eliminaron el caso reproducible con mp_restartgame.

======================================================================
15. OPTIMIZACIONES DE RENDIMIENTO DEL BRIDGE
======================================================================

Se detectaron tirones por dos causas:

1. Knife dry-run recorria entidades/modelos y escribia al log repetidamente.
2. El snapshot se parseaba y publicaba cada segundo aunque fuera identico.

Correcciones:

- Se eliminaron los dry-run periodicos del ciclo de produccion.
- El snapshot solo se publica si cambia su hash.
- El evento de killfeed se procesa una vez con pre-hook activo.
- Mientras el Butterfly permanece equipado se usa un estado estable.
- El recorrido pesado de HudModelArms y las lecturas de modelos solo ocurren al
  equipar, recoger, reaparecer o cambiar de entidad.
- La validacion estable del mismo cuchillo se reduce a handle, definition y
  subclass, con intervalo relajado.

Resultado comprobado:

- Sin tirones con Butterfly equipado.
- Sin tirones con el cuchillo en el suelo.
- Sin tirones al usar otras armas.
- Animaciones, HUD y killfeed se mantienen correctos.

16. PANIC Y LIMPIEZA
======================================================================

Se agrego una pestana Home como primera pestana del menu.

Incluye:

- Panic button.
- Checkbox/bind configurable.
- Tecla default END.

8. Se detiene el servidor IPC y se liberan sus recursos.

18. AUTO OFFSETS Y SNAPSHOT RUNTIME
======================================================================

OverlayAI mantiene el sistema de offsets generado por cs2-dumper. Los offsets
se validan y cargan desde la ruta output de la compilacion exterior.

El snapshot IPC transporta los offsets runtime requeridos por el bridge, entre
ellos:

- entity list
- local controller y local pawn
- player pawn handle
- team y life state
- spawn time
- game scene node y model state
- owner entity
- HudModelArms y arbol de scene nodes
- WeaponServices y active weapon
- subclass ID
- attribute manager e item view
- item definition index
- fallback paint kit, seed y wear

El bridge no lleva una segunda copia manual permanente de esos offsets. Las
firmas de funciones internas siguen siendo dependientes de build y se validan
por cantidad de coincidencias antes de habilitar la funcion.
