==================================================
CONTEXTO DEL PROYECTO
==================================================

OverlayAI es actualmente un Overlay externo con algunas funciones similares a un "cheat o hack" para CS2 escrito en C++ y construido mediante una solución de Visual Studio. No utilizo CMake.

El programa usa ImGui para su interfaz y puede leer o escribir memoria del proceso de CS2. No ejecuta normalmente código dentro del hilo del juego.

La pestaña Inventory Changer ya tiene:

- Un catálogo offline de aproximadamente 2290 artículos.
- Music Kits.
- Skins de armas.
- Cuchillos.
- Guantes.
- Agentes.
- Filtros por categoría.
- Filtros por rareza.
- Ordenamiento.
- Buscador.
- Definition index.
- Paint kit.
- Wear.
- Seed.
- Variantes StatTrak y Souvenir cuando corresponden.
- Una colección local persistente mediante Configs.
- Posibilidad de duplicar variantes.
- Estado de objeto equipado.
- Imágenes de los artículos obtenidas desde el catálogo.
- Aplicación local funcional de Music Kits.

Actualmente solo los Music Kits pueden aplicarse realmente al cliente y con limitaciones ya que en el menú principal no se aplica la musica.

Las armas, cuchillos, guantes y agentes todavía funcionan como catálogo y colección local. Aún no existe integración visual con Panorama ni aplicación completa de esos objetos.

La interfaz actual de ImGui funciona como herramienta administrativa y de depuración, pero no quiero que sea la experiencia final del usuario.

==================================================
OBJETIVO EXACTO
==================================================

Quiero simular localmente la experiencia completa del inventario de CS2.

No quiero que el objeto exista realmente en Steam.

No necesito que Steam, el Game Coordinator, el servidor ni otros jugadores crean que el objeto existe.

El efecto debe ser exclusivamente local, pero quiero que visualmente parezca integrado en la interfaz oficial de CS2.

El flujo deseado es:

1. Seleccionar un artículo desde OverlayAI.
2. Configurar su wear, seed y variantes válidas.
3. Pulsar “Añadir a mi colección”.
4. Mostrar dentro de Panorama una presentación similar o la presentación de  “NEW ITEM”.
5. Al continuar, el objeto debe aparecer en un inventario local visualmente integrado con el inventario de CS2.
6. El usuario debe poder seleccionar el objeto.
7. Debe poder inspeccionarlo.
8. Debe poder equiparlo para T, CT o ambos cuando corresponda.
9. Debe poder desequiparlo.
10. Debe poder eliminarlo de la colección local.
11. La colección y el loadout deben persistir entre ejecuciones.
12. Al cerrar o desactivar OverlayAI, los overrides y elementos visuales temporales deben limpiarse correctamente.

Quiero que el resultado se sienta como un objeto individual adquirido, no como un botón genérico de “Apply skin”.

Aunque el usuario tenga dos artículos con el mismo definition index y paint kit, deben ser instancias locales diferentes.

Ejemplo:

- Butterfly Knife | Doppler, wear 0.008, seed 421.
- Butterfly Knife | Doppler, wear 0.031, seed 127.

Ambas deben tener identificadores locales diferentes y poder configurarse por separado. OverlayAI deberia poder diferenciar distintos estados de la misma skin como por ejemplo:

- Butterfly Knife | Doppler (phase 4), wear 0.008, seed 421.

- Butterfly Knife | Doppler (phase 1), wear 0.008, seed 421.

==================================================
MODELO CONCEPTUAL
==================================================

Debes diferenciar claramente cuatro conceptos:

1. Local Item ID
2. Faux Item ID
3. InventoryAPI
4. SOCache

--------------------------------------------------
LOCAL ITEM ID
--------------------------------------------------

Cada instancia creada por OverlayAI debe tener un identificador local propio.

Ejemplo conceptual:

struct LocalInventoryItem
{
    uint64_t localId;

    int definitionIndex;
    int paintKit;

    float wear;
    int seed;

    bool statTrak;
    int statTrakCount;
    bool souvenir;

    std::string customName;

    std::vector<LocalSticker> stickers;

    ItemTeam equippedTeam;
    int64_t acquiredAt;
};

El localId es la verdadera identidad de la instancia dentro de OverlayAI.

No debe confundirse con un Steam item ID.

El loadout local debe referenciar localId, no solamente definition index y paint kit.

Ejemplo:

loadout.terroristKnife = localId;
loadout.counterTerroristKnife = localId;

--------------------------------------------------
FAUX ITEM ID
--------------------------------------------------

Un Faux Item ID describe sintéticamente un artículo mediante definition index y paint kit.

Puede servir para:

- Resolver nombres.
- Resolver imágenes.
- Obtener determinada información visual.
- Solicitar previews cuando la API compatible lo permita.
- Alimentar paneles Panorama propios.

No representa propiedad real.

No debe tratarse como una instancia auténtica.

No debe asumirse que añadir un Faux Item ID aumenta InventoryAPI.GetInventoryCount().

El programa debe mantener separados:

- localId: identidad de la instancia local.
- fauxId: descriptor visual compatible con algunas funciones de CS2.
- steamItemId: solamente para objetos auténticos que ya existan, nunca para los falsos.

--------------------------------------------------
INVENTORYAPI
--------------------------------------------------

InventoryAPI es la interfaz utilizada por los scripts de Panorama para consultar y operar sobre objetos conocidos por el cliente.

Panorama utiliza funciones como:

- GetInventoryCount()
- GetInventoryItemIDByIndex()

No debe asumirse que InventoryAPI funciona como base de datos modificable.

No debe asumirse que pasarle un Faux Item ID añade automáticamente el artículo al inventario nativo.

Debe investigarse qué funciones existentes aceptan Faux Item IDs para:

- Nombre.
- Imagen.
- Descripción.
- Preview.
- Modelo.
- Equipamiento visual local.

Toda función encontrada debe documentarse con:

- nombre;
- archivo donde se usa;
- argumentos;
- resultado;
- limitaciones;
- versión o build donde fue comprobada.

--------------------------------------------------
SOCACHE
--------------------------------------------------

SOCache es la caché local de shared objects sincronizados con los servicios de Valve.

Insertar correctamente un objeto falso en SOCache requeriría, como mínimo:

- Construcción correcta de CEconItem.
- ABI interna correcta.
- Ownership de memoria correcto.
- Obtención del type cache apropiado.
- Registro de la instancia.
- Notificación a listeners.
- Eliminación segura.
- Compatibilidad con cada actualización de CS2.

cs2-dumper proporciona offsets y campos de estructuras, pero no proporciona necesariamente:

- constructores internos;
- destructores;
- type cache;
- callbacks;
- listeners;
- funciones de registro;
- ABI estable.

SOCache no debe ser la primera implementación.

En la primera etapa debe tratarse únicamente como investigación.

No insertes objetos en SOCache sin que yo lo apruebe expresamente después de revisar un informe técnico separado.

ARQUITECTURA DESEADA
==================================================

La arquitectura preferida es:

OverlayAI externo
    |
    | Catálogo, colección, configuración y persistencia
    |
    | IPC local validado
    v
Frontend Panorama local
    |
    | Ventana NEW ITEM
    | Inventario visual local
    | Filtros y tarjetas
    | Inspect
    | Equipar y desequipar
    v
Acciones enviadas nuevamente a OverlayAI
    |
    | Aplicación local del objeto seleccionado
    v
CS2

OverlayAI debe seguir siendo la fuente de verdad para:

- catálogo;
- colección;
- instancias locales;
- loadout local;
- configuración;
- validación;
- persistencia.

Panorama debe ser principalmente un frontend.

Panorama no debe conocer offsets ni escribir memoria.

Panorama envía acciones de alto nivel como:

- inventory.added
- inventory.remove
- inventory.inspect
- inventory.equip
- inventory.unequip
- inventory.request_refresh
- inventory.close_reveal

OverlayAI responde con estados como:

- inventory.snapshot
- inventory.item_added
- inventory.item_removed
- inventory.loadout_changed
- inventory.apply_success
- inventory.apply_failed

El protocolo debe estar versionado y validar todos los mensajes.

No se deben aceptar campos arbitrarios sin comprobación.

==================================================
VALIDACIÓN
==================================================

Antes de aceptar un artículo:

- El definition index debe existir.
- Debe corresponder con su categoría.
- El paint kit debe ser compatible.
- El wear debe respetar min_float y max_float.
- Seed debe estar dentro del rango permitido.
- StatTrak solo debe habilitarse si la variante existe.
- Souvenir solo debe habilitarse si la variante existe.
- Los cuchillos deben conservar modelos compatibles.
- Los agentes deben respetar facción.
- Los Music Kits deben utilizar IDs válidos.
- Stickers, charms y parches deben respetar slots y categoría.
- La rareza y calidad deben provenir del catálogo, no ser arbitrarias.

La validación debe ejecutarse:

1. Al crear.
2. Al editar.
3. Al cargar Configs.
4. Antes de enviar a Panorama.
5. Antes de aplicar un override.

Los objetos inválidos cargados desde una configuración antigua no deben provocar crashes.

Deben marcarse como:

- válido;
- desactualizado;
- incompatible;
- incompleto.

PROTOCOLO IPC
==================================================

Diseña primero el protocolo de comunicación.

Cada mensaje debe incluir:

- protocol_version;
- message_type;
- request_id;
- payload.

Ejemplo conceptual:

{
    "protocol_version": 1,
    "message_type": "inventory.item_added",
    "request_id": 1024,
    "payload": {
        "local_id": 1842,
        "definition_index": 515,
        "paint_kit": 421,
        "wear": 0.008,
        "seed": 412,
        "stattrak": false
    }
}

Requisitos:

- Límites de tamaño.
- Validación de tipos.
- Validación de rangos.
- Manejo de mensajes desconocidos.
- Timeouts.
- Reconexión.
- Snapshot completo al reconectar.
- Evitar duplicados.
- Idempotencia cuando corresponda.
- Logging.
- Compatibilidad de versiones.

No envíes punteros entre procesos.
